# 默认分享地址与二维码

状态：已实现第一阶段的地址排序、保守标签和 Slint 原生二维码；网络变化、热点及成功使用反馈仍属于规划。宿主使用实际端口生成 IPv4 候选，Slint 显示当前连接的标签、地址、二维码及其他连接列表。FileInfra 的经验是优先显示 Wi-Fi 地址，并保留仍然可用的手动选择；后续工作在此基础上处理热点、多网卡和网络变化。

Linux/Android 读取系统网卡事实区分 Wi-Fi、有线、虚拟与未知，不根据网卡名称猜测。当前顺序为 Wi-Fi、有线、未知、未启用连接、虚拟，回环最后；同级按名称和地址稳定排序，重复地址保留最合适的标签。Windows/macOS 尚无完整类型适配，缺少事实时显示普通网络连接。二维码只编码选中的 URL，使用四模块留白和所有主题下的白底深色模块，不包含访问密钥。仅本机地址显示说明而不提供远端扫码二维码。

手动切换只改变当前会话显示的地址和二维码，保留同一监听及传输。下一阶段再加入网络事件、热点确认、近期接入与实际成功使用信号；跨会话选择尚不保存。现有 `HostStatus.addresses` 的字符串数组形状不变，Slint 使用带标签的进程内 `SessionSnapshot.endpoints`。

## 要解决的问题

用户希望接收设备扫码即可连接，不必理解 IP 地址和网卡。设备刚开启热点或连接新 Wi-Fi，确实可能是在准备传输，但新出现的接口也可能是 VPN、容器或虚拟机。单凭连接时间、地址排序或互联网默认路由，不能可靠判断接收设备在哪个网络。

推荐只决定显示哪个分享地址。服务仍按照用户选择的本机或局域网模式运行，二维码使用实际绑定端口；推荐不修改系统路由、不切换网卡绑定，也不迁移正在运行的服务。

## 后续推荐规则

先确认候选接口已启用、地址有效且属于当前允许分享的范围，再评估以下信号。没有互联网的热点和局域网仍然有效。

| 信号 | 处理方式 |
| --- | --- |
| 用户在本次分享中明确选择的连接 | 连接仍有效时保持最高优先级，不因新网卡出现而更换 |
| 应用明确创建、或系统公开接口能确认的当前热点 | 强信号，适合推荐给正在连接该热点的接收设备 |
| 刚接入的普通 Wi-Fi、网线或 USB 网络 | 提高优先级，但结合接口类型、连接状态和已有选择；新出现不等于更适合 |
| 当前同一连接曾成功完成远端传输 | 作为有效性证据；身份或地址变化后重新确认，不按旧 IP 永久记忆 |
| 物理网络及适用的本地路由 | 用于同等候选的排序；互联网默认路由只作辅助信号 |
| VPN、容器、虚拟机、仅主机网络 | 不自动压过普通局域网；用户有意通过这些连接分享时仍可手动选择 |
| 接口类型或热点状态无法确认 | 显示普通“网络连接”标签，降低判断置信度，不根据网卡名称伪造 Wi-Fi 或热点结论 |

第一版采用可解释的固定规则，避免机器学习、联网评分或后台测速。近期接入的权重随时间降低；相近候选保持稳定的顺序，不因地址枚举顺序而来回切换。跨会话历史选择只在平台能够确认同一连接时复用；只匹配 IP 地址或网卡名称不够。

## 后续连接体验

只有一个可信候选时，直接显示二维码和连接类型。存在多个候选时，显示一个推荐项及简短原因，例如“热点 · 最近开启”或“Wi-Fi · 本次已连接”，并提供“切换连接”。不确定时仍允许扫码尝试，界面说明选择依据，不宣称已保证可达。

切换列表优先显示 Wi-Fi、热点、网线等已确认的类型；系统提供的连接名称作为辅助信息，IP 地址放在次要位置。默认二维码不包含访问密钥。仅本机模式不显示供其他设备扫描的局域网二维码。

用户手动选择、复制或保存分享地址后保持该选择，直到连接失效或用户重新选择自动推荐。已有远端传输时避免自动更换仍有效的默认项。接口断开后立即撤销失效地址，提示连接变化，再选择有效候选；不以地址显示变化承诺中断的系统网络已经恢复。

## 模块边界与性能

平台适配器提供接口、地址、连接类型、适用路由和可获得的连接变化事件。独立选择器只处理这些快照、用户选择和可验证的使用反馈，输出候选、推荐理由及判断置信度。二维码组件只接收最终 URL，产品名称和 HTTP 文件模块均不参与网络排序。

各平台公开 API 和权限不同。尤其 Android 的 Wi-Fi 信息和系统热点状态不能假定普通应用总能取得；缺失信息必须保守降级，不能为了二维码擅自增加敏感权限。具体 Windows、Linux、macOS、Android 适配在目标系统上验证后分别标记支持。

优先订阅网络变化，合并短时间内的重复事件，并在启动或用户重新选择时刷新。降级刷新只在相关界面可见时进行，频率有界；不增加持续高速轮询、扫描其他设备、ping 广播或后台传输基准。

未来“成功使用”反馈需来自服务自己观察的连接和已完成操作，不能信任客户端传入的 Host、转发头或自称网卡信息。运行中的下载响应体、上传和管理任务都需要纳入活动归属，单凭最后一条日志时间不能证明空闲。第一版反馈保留在本地会话内；任何持久记录或新增原生权限都要同步更新隐私清单。

## 验收范围

现有规则测试覆盖候选排序、去重、保守分类及实际端口。后续测试需覆盖单 Wi-Fi、网线与 Wi-Fi 并存、新热点、无互联网热点、新 VPN、虚拟网卡、地址续租、断开重连、手动锁定、历史选择失效和接口信息缺失。实际系统测试分别验证接口识别、事件订阅、权限降级和二维码 URL；真实双设备扫描及传输成功才建立网络可达性证据。

第一阶段的实现不能替代后续平台、网络变化及双设备验收；Tauri 过渡宿主仍只消费地址列表。平台与商店边界继续见[平台状态](platforms.md)及[需求](requirements.md)。
